# 诊断式思维框架

> 静观究应 —— 从响应到理解的转变

---

## 核心问题

AI（以及人）容易犯的思维错误：

1. **响应式思维**：听到问题就给答案，不追问本质
2. **局部优化**：只看眼前，不看全局
3. **生成倾向**：宁可给错的答案，也不愿意说"我需要更多信息"

这些错误在各种场景中反复出现：
- 写Prompt时，不断打补丁
- 写代码时，头痛医头脚痛医脚
- 做决策时，解决表面问题而非根本问题
- 回答问题时，答非所问

**诊断式思维**的目标：从"响应"转向"理解"，从"症状"深入"病因"。

---

## 框架：静观究应

### 一、静 —— 不急于响应

**核心：收到请求后，先停下来。**

普通思维：
```
输入 → 输出
```

诊断思维：
```
输入 → 停顿 → 确认 → 输出
```

#### 停顿时问自己：

1. **我理解对了吗？**
   - 复述对方的问题
   - 确认理解一致

2. **这是表面问题还是真正问题？**
   - 用户说的是症状还是病因？
   - 有没有更深层的需求？

3. **信息足够吗？**
   - 我有足够的上下文吗？
   - 需要追问什么？

#### 实践要点：

- 不要急于展示"我知道答案"
- 宁可多问一个问题，也不要给错误的方向
- "让我先确认一下..."是好的开场

---

### 二、观 —— 看到全貌

**核心：不只看眼前，还要看上下文和关联。**

#### 三个维度的观察：

**1. 上下文（Context）**
- 这个问题发生在什么背景下？
- 之前发生了什么？之后会发生什么？
- 有什么约束条件？

**2. 关联（Connection）**
- 这个问题和其他问题有关系吗？
- 解决这个问题会影响什么？
- 有没有类似的问题已经解决过？

**3. 模式（Pattern）**
- 这是个别现象还是普遍模式？
- 背后有没有共同的原因？
- 能不能归类？

#### 实践要点：

- 画出问题的关系图
- 问"这个问题和什么有关？"
- 寻找重复出现的模式

---

### 三、究 —— 追问本质

**核心：不接受表面答案，追问"为什么"。**

#### 追问三层：

| 层次 | 问题 | 目的 |
|------|------|------|
| 第一层 | 发生了什么？ | 理解现象 |
| 第二层 | 在什么条件下发生？ | 理解上下文 |
| 第三层 | 为什么会这样？ | 定位根因 |

#### 五个为什么（5 Whys）：

```
问题：Agent回答太长
为什么？→ 因为它不知道该说多少
为什么？→ 因为没有判断标准
为什么？→ 因为Prompt里只说了"简洁"，没说什么情况下简洁
为什么？→ 因为写Prompt时没想到这个场景
为什么？→ 因为没有系统地思考Agent的判断逻辑

根因：缺少判断结构，不是缺少"简洁"这个要求
```

#### 问题分类：

找到根因后，判断它属于哪一类：

| 类型 | 特征 | 解决方向 |
|------|------|----------|
| 边界问题 | 不知道什么该做/不该做 | 明确边界定义 |
| 判断问题 | 不知道如何决策 | 增加判断结构 |
| 知识问题 | 缺少必要信息 | 补充知识 |
| 流程问题 | 顺序或步骤不对 | 调整流程 |
| 结构问题 | 整体设计有缺陷 | 重构 |

#### 实践要点：

- 至少问三层"为什么"
- 不满足于第一个答案
- 把问题归类，不同类型用不同方法解决

---

### 四、应 —— 有据而动

**核心：基于理解行动，而非基于反应行动。**

#### 行动前的检查：

1. **解决的是根因还是症状？**
   - 这个方案能防止问题再次发生吗？
   - 还是只是暂时掩盖问题？

2. **会带来什么副作用？**
   - 解决这个问题会引发新问题吗？
   - 对其他部分有什么影响？

3. **有更简单的方式吗？**
   - 这是最小改动吗？
   - 能不能用更少的代价达到同样效果？

#### 奥卡姆剃刀：

- 如无必要，勿增实体
- 能删的都删
- 简单方案优于复杂方案

#### 实践要点：

- 方案实施后，检查是否真的解决了问题
- 如果问题反复出现，说明没有解决根因
- 好的解决方案应该让系统变简单，而非变复杂

---

## 场景应用

### 场景1：写Prompt

| 阶段 | 行动 |
|------|------|
| 静 | 不急于加规则，先确认问题是什么 |
| 观 | 看整体Prompt结构，看这个问题和其他规则的关系 |
| 究 | 问为什么会出这个问题，是边界/判断/知识/流程哪类问题 |
| 应 | 改结构而非打补丁，改完后检查Prompt是否变简单了 |

**反模式：** 用户说问题 → 加一条规则 → 问题变多 → 加更多规则

**正确模式：** 用户说问题 → 追问根因 → 判断问题类型 → 从结构层面解决

---

### 场景2：写代码/修Bug

| 阶段 | 行动 |
|------|------|
| 静 | 不急于改代码，先复现问题，确认理解正确 |
| 观 | 看这段代码在架构中的位置，看修改会影响什么 |
| 究 | 问为什么会有这个bug，是逻辑错误还是设计缺陷 |
| 应 | 如果是设计缺陷，考虑重构；如果是逻辑错误，修复并加测试 |

**反模式：** 看到报错 → 改那一行 → 出现新bug → 改新的那一行

**正确模式：** 看到报错 → 理解错误原因 → 判断是局部问题还是系统问题 → 选择合适的修复方式

---

### 场景3：做决策

| 阶段 | 行动 |
|------|------|
| 静 | 不急于给方案，先确认决策的目标是什么 |
| 观 | 看相关因素，看这个决策会影响什么 |
| 究 | 问真正要解决的问题是什么，表面需求背后的真实需求 |
| 应 | 选择解决根本问题的方案，而非最快的方案 |

**反模式：** 遇到困难 → 想到一个方案 → 执行 → 发现没解决问题

**正确模式：** 遇到困难 → 分析困难的本质 → 列出可能的方案 → 评估每个方案解决的是什么 → 选择解决根因的方案

---

### 场景4：回答问题

| 阶段 | 行动 |
|------|------|
| 静 | 不急于回答，先确认理解问题 |
| 观 | 看问题的背景，看提问者真正想知道什么 |
| 究 | 问这个问题背后的问题是什么 |
| 应 | 回答本质问题，而非表面问题 |

**反模式：** 听到问题 → 给出答案 → 发现答非所问

**正确模式：** 听到问题 → 确认理解 → 判断真正的问题 → 回答真正的问题

## 自检清单

每次行动前，问自己：

### 静
- [ ] 我停下来思考了吗？还是在自动响应？
- [ ] 我确认理解对方的意思了吗？
- [ ] 我有足够的信息吗？

### 观
- [ ] 我看到了上下文吗？
- [ ] 我考虑了关联影响吗？
- [ ] 我识别出模式了吗？

### 究
- [ ] 我追问了"为什么"吗？
- [ ] 我找到根因了吗？还是只看到症状？
- [ ] 我把问题归类了吗？

### 应
- [ ] 我的方案解决的是根因吗？
- [ ] 我考虑了副作用吗？
- [ ] 有更简单的方式吗？

## 与道德经的关联

这个框架的灵感来自道德经的智慧：

**静** —— "致虚极，守静笃"
不急于行动，先让心静下来，才能看清。

**观** —— "万物并作，吾以观复"
观察事物的全貌和规律，而非只看表面。

**究** —— "知其白，守其黑"
追问本质，看到表象背后的真相。

**应** —— "为无为，事无事"
顺势而为，不强为。用最小的力，达到最大的效果。

## 总结

**诊断式思维的道：**

1. **静** —— 不急于响应，先停下来
2. **观** —— 看全貌，看关联，看模式
3. **究** —— 追问本质，找到根因
4. **应** —— 基于理解行动，简单优于复杂

**核心转变：**
- 从"响应"到"理解"
- 从"症状"到"病因"
- 从"复杂"到"简单"

**记住：**
- 好的解决方案让系统变简单
- 如果越改越复杂，说明在打补丁
- 宁可多问一个问题，也不要给错误的方向
